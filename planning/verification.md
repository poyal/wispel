# Wispel 1.0 개발 후보 검증

아이폰에서 시작해 Windows를 거쳐 Android 시스템 알림으로 표시되는 경로를 LAN에서 확인했습니다. 이 결과는 개발 후보에 대한 기록입니다. 실기기 배포 판정에는 잠긴 셀룰러 아이폰과 페어링한 워치에서의 관찰이 남아 있습니다.

## 시험 환경

시험일은 한국 시간 2026년 11월 23일 밤부터 24일 새벽까지입니다.

| 역할 | 환경 |
|---|---|
| 중계 | Windows x64, .NET 10, LocalService로 등록한 독립 시험 서비스와 SQLite. Mac에서 Windows IP의 TCP 7443으로 직접 연결 |
| 아이폰 | Mac mini의 Xcode 27.2, iOS 27.2 시뮬레이터. Swift 단위 시험, XCUITest, 시스템 단축어 앱과 실제 알림 배너 사용 |
| 안드로이드 | Windows의 Android 폰 에뮬레이터, 실제 알림 접근·직접 수신 서비스·알림 관리자 사용 |
| 워치 | Wear OS 에뮬레이터 부팅. 공식 동반 앱을 설치하는 단계에서 Google Play 계정 로그인이 필요해 본폰 브리징 플래그까지 검증 |

## 실행 결과

| 시나리오 | 관찰 |
|---|---|
| 서버와 네이티브 코드 | 서버 18건, Kotlin 단위 3건, Android 기기 계측 3건, Swift 단위 3건 통과. Windows x64 자체 포함 게시와 Android 디버그 APK 생성. iOS 시뮬레이터 및 서명 없는 실기기 대상 Release 빌드 성공 |
| 최초 등록과 전달 | 아이폰에서 일회용 등록 주소를 열어 역할 확인 후 시험 발송. Windows가 접수하고 Android가 같은 이벤트를 처리해 확인 응답. 단축어 받기 5개 버튼 모두 올바른 종류의 설정 화면을 엶 |
| 보관함 단축어 5개 | iOS 파일 앱에서 서명 파일 5개를 각각 가져와 최초 동작 실행을 허용. 카카오톡·문자·Slack·메일이 해당 종류로 도착. 전화 텍스트 입력 연결을 수정한 최종 파일은 일반 착신과 `QA\n부재중 전화`를 각각 전화·부재중 전화로 전달. 여섯 종류 모두 Android 확인 |
| 아이폰 오프라인 발송 | Windows 서비스를 중지하고 아이폰 시험 발송 화면에서 발송 대기 표시 확인. 서비스를 복구하고 아이폰 앱을 재실행한 뒤 카카오톡 한 건만 Android 확인 상태에 도달 |
| 종류·권한·중복 | 전화·부재중·문자·Slack·카카오톡·메일 6종 모두 본폰 확인. 같은 ID 재전송, 다른 내용으로 같은 ID 사용, 발신 기기 위조, 재사용 QR, 허용하지 않은 본문 필드 처리 확인 |
| 연속 수신 | 독립 이벤트 120건 모두 Android 확인. 순차 요청 시작부터 서버에서 본폰 확인을 관찰하기까지 중앙값 1.079초, 95백분위 1.256초, 최대 1.671초. 서버 조회 간격을 포함한 LAN 수치 |
| 서버 재시작·본폰 오프라인 | Android 앱을 강제 종료하고 시험 서비스를 중지·재시작. 저장된 이벤트가 복구 후 약 81초에 지연 채널로 전달되고 같은 ID로 확인 |
| 절전 | 본폰 에뮬레이터에서 화면 잠금과 강제 Doze를 적용. 한 건이 12초 후 조회에서 이미 확인 상태. 물리 기기의 제조사별 절전 정책은 별도 시험 대상 |
| 큰 글자 | Android 글자 크기 150%에서 최근 알림 → 기기 설정 → 워치에 표시로 이동해 카카오톡 설정에 접근. 시험 후 이전 글자 크기로 복구 |
| Android 수신 설정 | 메일 본폰 전용, 카톡 워치 전달 허용을 시스템 알림 플래그에서 관찰. Slack 일시정지·재개와 문자 끄기·켜기에서 실제 게시 여부 일치. 기기별 집계, 기록 끄기·삭제 뒤 재전송은 계측 시험 통과 |
| Mosaic 시안과 본폰 표시 | 아이폰 단축어에서 문자 1, 메일 1, Slack 2, 부재중 전화 1, 카카오톡 3건을 차례로 실행. 확인 응답 8건과 본폰 타일의 순서·건수 대조. 본폰의 독립 표시 시험 버튼으로 실제 시스템 알림도 게시 |
| Android 발신 | 에뮬레이터의 기본 문자·전화 앱으로 문자, 전화 알림, 부재중 알림 분류 관찰. 메시지 앱이 이전 대화를 다시 게시하는 문제를 재현·수정. 같은 번호·같은 내용으로 보낸 문자 2건이 서로 다른 2개 이벤트로 접수 |
| Android → iOS | Android 시스템에서 합성 메일 알림을 게시해 실제 알림 리스너로 수집. Windows의 해당 레코드에서 운영 코드가 APNs 페이로드를 생성. 이를 시뮬레이터에 주입해 iOS 배너와 같은 이벤트의 HTTPS 확인 응답을 관찰. 시험 이름·본문 표식이 전달 데이터에 없음을 확인 |
| APNs 공급자 | P-256 JWT 서명, HTTP/2 요청, 공급자 성공·토큰 거부·토큰 만료·일시 실패를 모의 전송으로 시험. 실제 Apple 접수에는 개발 팀의 APNs 자격이 필요 |
| 운영 점검 | 별도 프로세스의 실제 웹에서 상태·이벤트 상세를 표시. 390px 너비에서 가로 넘침 없음. 권한 주소 없는 요청 404, 변경 메서드 405, 시험 서비스 중단 시 503, 복구 후 200 |

## 실기기에서 남은 배포 기준

시뮬레이터를 재시작하자마자 단축어 실행 URL 6개를 3초 간격으로 열었을 때 첫 조회에서는 3건, 뒤이은 조회에서 카카오톡까지 4건이 확인됐습니다. 이 실행의 전화 2건은 서버에서 찾지 못했습니다. 같은 최종 앱에서 앞선 확인을 기다린 뒤 실행한 6종은 각각 한 건씩 통과했습니다. 실제 알림 자동화의 잠금·재시작 직후 연속 입력도 배포 전에 대조합니다.

- 사용자 아이폰(iOS 27.2.1)에서 전화·카카오톡 알림 자동화가 작동했고, 착신과 종료 시점의 알림 및 마지막 줄의 `부재중 전화`가 관찰됐습니다. 위스펠 설치 후 셀룰러·잠금 상태에서 전화, 문자, 카카오톡, Slack DM·멘션, 메일플러그 새 메일을 각각 발생시켜 본폰 표시 횟수를 확인합니다.
- 집 밖에서 연결할 공인 IP 또는 VPN을 정하고 셀룰러에서 시험합니다. 이번 LAN 시험은 외부 네트워크의 도달성을 판정하지 않습니다.
- 본폰에 실물 Wear OS 워치를 연결해 카카오톡은 양쪽, 메일은 본폰에만 표시되는지 확인하고 전화 채널의 실제 진동을 관찰합니다.
- 아이폰 본폰 방향은 배포 서명과 APNs 자격을 설정해 잠긴 실기기에서 실제 Apple 접수 및 배너를 확인합니다. 일부 제조사에서 전화 앱이 통화 중 상태를 여러 번 게시하는 방식과 장시간 백그라운드 수신도 확인합니다.
